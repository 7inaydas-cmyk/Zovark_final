## Why

The previous change (`apply-migrations-054-071-with-ledger`, shipped earlier today) shipped `migrations/072_schema_migrations_ledger.sql` with a static backfill block that marked all migrations numbered `000_*` through `053_*` as `source='init_sql', applied_at='2026-01-01T00:00:00Z'`. The assumption was *"init.sql ≈ migrations 001–053 hand-merged at some past date"*. A read-only fingerprint audit on this branch (2026-04-13) shows that assumption is **partially false**.

### Evidence

A 30-migration spot-check against the live dev DB found **15 of the 30 marked-as-init_sql migrations have no schema fingerprint in the database**. The drift starts around migration 033 — everything before is fine, the 033–053 range is mostly broken:

### Why this happened

`migrations/072_schema_migrations_ledger.sql` (shipped today) hard-coded the init.sql era as a static `INSERT ... VALUES (...)` block, generated by `ls migrations/0[0-5]*.sql | sort -V` at proposal-write time. The list captures *every file in that range* as if `init.sql` had been kept up to date with each one. In reality, `init.sql` is a hand-merged frozen snapshot that was last touched somewhere around migration 032. After that, contributors added migration files under `migrations/*.sql` but did NOT roll their changes back into `init.sql` — and operator workflow has historically been to manually apply individual migrations with `psql < f`, leaving no trail.

The previous change's central assumption — *"init.sql backfill = files 000-053 by static list"* — is therefore a confidence-level overshoot. The correct rule should have been *"init.sql backfill = exactly the migrations whose schema fingerprint is observable in the live DB, computed at backfill time, not hard-coded"*.

### What this is blocking

`POST /api/v1/tasks` succeeds end-to-end again at the API layer (the previous fix worked). But the worker now fails at Stage 5 STORE on every workflow with `column "needs_human_review" of relation "agent_tasks" does not exist`, because migration 040 was falsely marked as init_sql and never actually ran. Probe rows sit at `pending` forever. The e2e probe stalls past its 120-second budget, `scripts/stack_healthcheck.sh --e2e` produces no output for 2.5+ minutes, and any workflow that touches the v3 governance layer (which sets `needs_human_review`) fails identically.

This is the second layer of an onion the previous change peeled. Fixing it is a prerequisite for any e2e benchmark, smoke test, or red-team rerun on this branch.

## What Changes

- **Add `scripts/audit_init_sql_backfill.sh`** — a strict bash script that walks every `schema_migrations` row with `source='init_sql'`, reads the corresponding `migrations/NNN_*.sql` file, extracts a representative fingerprint (the first table name from `CREATE TABLE`, or the first column from `ALTER TABLE … ADD COLUMN`, or the first index name from `CREATE INDEX`), and queries the live DB to verify the fingerprint actually exists. Output: a table per row with `present` / `MISSING` status, plus a final summary count and an exit code (0 if all present, 1 if any missing). Read-only.
- **Add `scripts/repair_init_sql_backfill.sh`** — a strict bash script that consumes the audit script's output (or re-runs the audit internally), `DELETE`s the falsely-marked ledger rows from `schema_migrations`, then re-invokes `scripts/apply_migrations.sh` so the runner picks up the now-unmarked migrations and applies them properly. Includes a `--dry-run` mode that prints the DELETE list without executing it.
- **Apply the audit + repair to the live dev DB** — produces the list of ~15+ falsely-marked migrations (already 15 spot-confirmed; the audit will find any others), DELETEs their ledger rows, and runs `apply_migrations.sh` to apply them with `source='migration_runner'`. Each migration runs in its own transaction; failures roll back cleanly.
- **Replace `migrations/072_schema_migrations_ledger.sql`'s static backfill block with a fingerprint-conditional one** — the static `INSERT … VALUES (...)` block is replaced with a `DO $$ … $$` block that, for each candidate filename, queries `information_schema.columns` / `information_schema.tables` / `pg_indexes` for that migration's fingerprint and only inserts the ledger row if the fingerprint exists. A fresh `docker compose down -v && up -d` followed by `scripts/apply_migrations.sh` will then produce a ledger that matches the actual DB state, regardless of how stale `init.sql` is at boot time. The fingerprint-per-migration table lives in 072 itself as a maintainable static map.
- **Add a Stage 0.7 to `scripts/e2e_probe.sh`** — a "schema_fingerprint" stage between Stage 0.6 (`schema_ledger`) and Stage 1 (`ingest`) that runs the audit script and fails if any init_sql-marked migration's fingerprint is missing. Stage 0.6 catches "filename in ledger" drift; Stage 0.7 catches "ledger lies about init.sql" drift. Together they prevent the failure mode that wasted the last hour from recurring.
- **Update `docs/RUNBOOK_HEALTHCHECK.md` `#schema-drift` section** to document the new failure mode (fingerprint mismatch on a row that *is* in the ledger), the diagnostic command (`scripts/audit_init_sql_backfill.sh`), and the fix (`scripts/repair_init_sql_backfill.sh`). Cross-link from the existing `#schema-drift` anchor; do not create a second anchor.
- **Update `CLAUDE.md` Known Issue #13** to mention the audit + repair scripts and the Stage 0.7 fingerprint check, not just the ledger existence check.

## Impact

- **Affected code**: 2 new bash scripts (`scripts/audit_init_sql_backfill.sh`, `scripts/repair_init_sql_backfill.sh`); modified `migrations/072_schema_migrations_ledger.sql` (replace static backfill with fingerprint-conditional `DO` block); modified `scripts/e2e_probe.sh` (Stage 0.7 + runner array + banner); modified `docs/RUNBOOK_HEALTHCHECK.md` (#schema-drift section); modified `CLAUDE.md` (Known Issue #13).
- **Affected DB state**: the repair script will DELETE roughly 15+ rows from `schema_migrations` (the falsely-marked init_sql rows whose fingerprints are missing) and re-INSERT them with `source='migration_runner'` after the runner applies them. Net change: ~15+ DDL operations on `agent_tasks` / `investigations` / `tenants` / `bootstrap_corpus` and a handful of new tables (`llm_audit_log`, `threat_type_aliases`, `system_configs`, `rate_limit_audit`). No business data touched.
- **Risk**: medium on first run, low after.
  - First-run vectors: (a) one of the missing migrations is non-idempotent or depends on a column that another missing migration is supposed to create (mitigation: the runner applies them in numeric order and each runs in its own transaction — failures roll back cleanly and name the failing file); (b) a `CREATE TABLE` in a missing migration collides with an `init.sql` table that has the same name but a different shape (mitigation: every migration in the 033-053 range uses `CREATE TABLE IF NOT EXISTS` or `ALTER TABLE … IF NOT EXISTS` per the previous change's spot-check); (c) the v3 governance code path was running against a DB without these columns for some unknown amount of time and the stored data is now in an inconsistent state (mitigation: probe the affected tables for orphaned rows before/after, and document any cleanup in §8).
  - Steady-state risk: zero. The fingerprint-conditional 072 cannot ship with false positives, the audit script is idempotent and read-only, and the Stage 0.7 probe catches future regressions.
- **Breaking**: none. Application code is unchanged. The audit + repair scripts are new operator tooling. The 072 rewrite is backwards compatible (existing ledger rows are untouched on re-run thanks to `ON CONFLICT DO NOTHING`); only fresh dev volumes get the new fingerprint-conditional behaviour.
- **Followup hooks**: production deploys of this change need the same audit + repair sequence. The audit is read-only and safe to run anywhere; the repair should be gated on a `pg_dump` snapshot per the prod runbook (out of scope, deferred to the prod-rollout follow-up).
